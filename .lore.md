### Architecture

<!-- lore:019f9453-e6f0-7027-9c6e-330b17e4cd5f -->
* **@loreai/pi compaction: extension hook + /v1/compact endpoint integration**: Pi's compaction goes through its extension API (\`pi.on('session\_before\_compact', ...)\`), not HTTP, so the gateway's usual HTTP-interception (pattern-matching Claude-Code-style requests) doesn't apply. Instead the hook calls the gateway's \`POST /v1/compact\` endpoint directly for a full LLM-synthesized summary (force-distill + knowledge + compact prompt), passing gatewayBase, sessionID, projectPath, previousSummary, firstKeptEntryId, tokensBefore from Pi's \`event.preparation\`. \`runCompaction()\` never throws and never writes to stdout/stderr (same TUI-safety pattern as elsewhere) — outcomes are: 404 \`session\_not\_found\` (session never routed through Lore, falls back to Pi's native compaction), thrown/network error (same fallback), or success returning \`{compaction: {summary, firstKeptEntryId, tokensBefore}}\`. Pi's native compaction (session-manager.ts) triggers when \`contextTokens > contextWindow - reserveTokens\` (default reserveTokens=16384), keeps \`keepRecentTokens\` (default 20000), and hard rule: never cuts at tool results (they must stay with their tool call). Settings path: \`~/.pi/agent/settings.json\` → \`{compaction:{enabled,reserveTokens,keepRecentTokens}}\`.

* **@loreai/pi extension: fetch interceptor + TUI-safe logging**: packages/pi/src/index.ts wires Lore into Pi via two mechanisms: (1) a fetch-level interceptor (installed once, guarded by fetchInterceptorInstalled) rerouting Pi's LLM calls through the Lore gateway while preserving original auth headers, adding x-lore-session-id/x-lore-project/x-lore-git-remote; (2) a session\_before\_compact hook calling gateway POST /v1/compact for a synthesized summary when Pi decides to compact. <!-- lore:019f94ce-f5fe-7902-85b3-f7a1ab729918 -->
* **binpatch bspatch: pread-window base read + reflink temp copy avoids ETXTBSY/AMFI**: binpatch's bspatch implementation never loads the old binary fully into the JS heap: it reads via positional pread through a single-block read-ahead cache (BlockCache class, blockCovers(start,end) guards start>=0 && start+len<=size, always returns exactly \`len\` bytes or fails), backed by a reflink copy served from OS page cache. Only referenced windows are pulled in, since bsdiff references the base mostly forward in many small windows. A reflink/temp-copy of the old binary is used specifically to avoid ETXTBSY (Linux) / AMFI SIGKILL (macOS) that occur when reading the binary currently being executed. Diff/extra blocks stream via node:zlib createZstdDecompress; output writes via node:fs createWriteStream with large highWaterMark to collapse syscalls; SHA-256 computed inline via node:crypto. Multi-patch chains keep intermediate results in memory (never hit disk) — only the final binary is persisted and hashed, avoiding per-hop disk writes/temp-copies/hash passes.
