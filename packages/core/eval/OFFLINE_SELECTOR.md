# Offline knowledge ranking pilot

Run `pnpm exec vitest run --config vitest.evals.config.ts packages/core/eval/offline-selector.eval.ts --printConsoleTrace`.

The eval seeds five hand-labeled, synthetic coding tasks in a test-owned SQLite database. Three tasks form the development split; two form the holdout split. Each task has one needed entry and misleading alternatives. It exercises the real `ltm.forSession()` selection and `searchRecall()` paths, with embeddings disabled, and prints one JSON measurement per task: missed needed entries, irrelevant injected entries, needed entries left in overflow, recall result rank, and elapsed time. It clears knowledge between cases so their FTS score normalization cannot depend on test order. No task text or knowledge content is logged or sent to Jev by this test.

An offline Jev evaluation of the same 16 candidate pairs separated these hand-authored labels, but that result is an easy-case check, not evidence that a local scorer has learned the judgment. The eval has no trained weights and makes no Jev call at runtime. Keep the development/holdout split fixed when testing a proposed local ranker. Compare it with the existing selector on the same eligible pool and token budget; score missed critical entries, harmful injections, recall coverage, latency, and prompt-cache cost. Require a larger, independently verified, permissioned corpus with corrections, near matches, version changes, mixed sources, and project boundaries before selecting a threshold or changing production ranking. Never export private session or knowledge text to an external judge without authorization.

## Read-only local volume audit (2026-10-08)

The user's local database was inspected with read-only SQLite queries; no stored message, knowledge text, or identifier was printed or sent to a judge. Among 1,400 sessions active in the preceding 30 days with at least five turns, the **latest saved state** had a median of 146 context-bound pinned entries (mean 133), a median of 30,966 context-bound tokens (mean 32,829), and a median of 15,982 stable-block tokens (mean 16,282). The stable block also contains preferences, entities, and a small catalog; it is not all knowledge-entry text. Across 1,399 sessions with recorded last-input usage, the sum of these two saved memory budgets was 32.2% of the sum of last-known input tokens. Saved state and last-known usage need not represent the same turn, so this is a footprint estimate, not a causal cost estimate.

For a deterministic sample of 341 sessions with a single verified project and tenant owner, 170 had enough FTS matches at both the first and last user messages to compare. For each message, an as-of-time FTS query considered only its own project and eligible global non-preference knowledge, excluded superseded versions, and matched pinned version IDs by stable `logical_id`. The mean eligible pool was 108.7 entries; the saved pins already covered 91.2% of it. They covered 92.0% of the last-message FTS top ten. This near-complete coverage shows that the present budget rarely forces meaningful selection in this sample. It does **not** show that 91.2% of the knowledge was useful: FTS relevance is a weak proxy, confidence comes from current metadata rather than historical snapshots, and the sample excludes short or nonmatching queries.

In 120 of those sessions, a top-20 FTS selection from the penultimate user message covered 59.9% of the final message's FTS top ten; a top-20 selection from the first user message covered 65.5%. A bare last-message query is therefore **not** supported as a better selector. This probe does not measure agent task success, retrieval from the real `forSession()` pipeline, embeddings, or whether late user messages are standalone task descriptions. Keep the current runtime budget until independently labeled, held-out tasks establish which omissions hurt agent work.

### Late-turn retrieval experiment

Compare a small initial context with targeted, **additive** post-turn retrieval on the same scoped candidate pools and task traces. Build the later query from the current task and recent turns, including files and tool failures when available, instead of the last user message alone. Search live knowledge plus allowed distillation candidates; preserve project/tenant, confidence, visibility, version, and standing-preference rules before ranking. Deduplicate by `logical_id`, reserve coverage for critical instructions, and leave unselected candidates discoverable by recall. Deliver genuinely new high-value entries at a safe message-tail boundary as a durable knowledge delta, without rewriting the pinned stable system block or repeating already delivered content. Bound the number and size of additions across turns. Compare with the present near-full injection on held-out agent tasks: critical omissions, wrong or stale advice, actual completed work, recall use, cache-aware token cost, and latency. Only choose a cutoff or reduce the initial budget after that comparison.

The initial implementation uses the latest real user task as the query (with the previous user turn for short continuations); direct core callers without a task hint use recent real user messages before old observations. Tool results do not become task queries. A changed task reselects context-bound entries and appends newly selected, previously unseen entries in an immutable durable delta. Repeated entries add no delta; the stable system block remains unchanged. The ninth distinct delta compacts the first eight and the new addition atomically, preserving earlier task additions. A synthetic four-turn gateway case proves that a tenant-routing entry reaches the model after a chart task; a six-topic case shows that the default budget can deliver all 36 seeded entries on the first injection, with no later additions. These tests prove delivery and cache behavior, not entry utility. The default injection budget remains unchanged because the five-case offline pilot misses both holdout critical entries, and no held-out agent-task outcome supports a smaller cap yet.
